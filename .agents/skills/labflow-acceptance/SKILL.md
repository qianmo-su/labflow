# 知序 LabFlow 排期验收

## 先把用户的意图写成可判定的条件

先读 `Schedule.java`、`Domain.java`、`PlatformTest.java` 和本文件。描述参与者、输入、初始状态、触发操作、预期返回和最终状态；尚未定义的规则交由需求方决定。参照已有项目结构，不自行扩展到按座位预约、节假日日历或校园身份系统。

## 两条核心规约

- **R1 开放节次。** 一次连续预约占用同一天的闭区间 `[from,to]`。已知房间开放 `[low,high]`，当且仅当 `low <= from <= to <= high` 时节次校验通过。相等表示只用一节，不是空区间。非法区间应抛出业务异常 `Rule`，状态码为 400。此处只规定节次，不保证日期、身份或冲突校验通过。
- **R2 重叠审批。** 同房间、同日，第 3 至 4 节和第 4 至 5 节可以同时待审。两位教师同时批准时，不指定赢家；只允许一份获批，另一份保留待审并报告第 4 节冲突。重新查询占用表应恰有两行。代码位置为 `Schedule.review`，既有验证入口是 `PlatformTest.concurrentApprovalsAreAllOrNothing`。

## 给编程智能体的任务输入

> 在 `edu.campus.lab` 包中生成 `BookingWindowSpecTest`。按 A1 至 A8 编写 JUnit 5 参数化测试，直接调用已有 `Schedule.periods`。每组输入显式写预期值；非法输入检查业务异常及 400。不要改业务实现，不启动 Spring 或数据库。输出可编译的 Java 文件、复测命令和按编号核对的结果。

本任务的产物是 `src/test/java/edu/campus/lab/BookingWindowSpecTest.java`。在源码工程目录执行 `mvn "-Dtest=BookingWindowSpecTest" test`。预期运行 8 项，失败、错误、跳过均为 0。用 `target/surefire-reports` 内的结果核对，不能以智能体口头判断代替执行。该命令不验证 R2；要验证 R2，应另行运行上文所指的集成测试。

## 失败后和高风险操作

先记录用例编号、输入、实际与预期的差异，再判断是规约有歧义、测试写错，还是实现有误。不要为了变绿修改预期。要检查测试是否能发现闭区间错误，可在一次性源码副本中模拟“右端不能取到”，只跑 R1；随后回到未改副本复核，不把模拟错误合入工程。

只读源码、本机编译和这组纯计算测试可直接进行。连接外部数据库、在已有库重建表、修改权限或公开发布代码，必须先说明具体目标、影响与恢复办法，由负责人明确批准。未获批准时使用本地隔离数据或停止该操作；不在报告和日志中记录凭据。
